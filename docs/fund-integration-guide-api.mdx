The Account Funding API integration lets your platform accept crypto and stablecoin deposits from end customers without building any custom frontend. Zero Hash handles the deposit, auto-converts the received asset to USD, and sweeps the converted balance to your platform's master ledger account — all automatically after a single deposit address is generated. This guide covers the full flow: participant setup, generating deposit addresses, monitoring webhooks, reconciling ledger movements, and querying settlements.

<Note>
  This guide assumes you are using the **Onboarding API (Reliance)** model, where your platform performs KYC using an external provider and passes the results to Zero Hash via API. If you use the Zero Hash KYC SDK for onboarding, see the [Account Funding SDK guide](/docs/fund-integration-guide-sdk).
</Note>

## Prerequisites

Before you begin, confirm the following with your Zero Hash representative:

<CardGroup cols={2}>
  <Card title="Webhooks configured" icon="bell">
    Ask your Zero Hash representative to enable **Onboarding** and **Account Funding** webhooks for your platform.
  </Card>
  <Card title="Signed agreements" icon="file-signature">
    Each customer must accept the `fund_auto_convert` agreement. Missing this agreement causes all `/fund` API calls to fail.
  </Card>
  <Card title="Permitted jurisdictions" icon="globe">
    Verify that your customers' states and countries are in Zero Hash's list of permitted jurisdictions before submission.
  </Card>
  <Card title="Platform credentials" icon="key">
    You have your `platform_code` and API credentials for the Zero Hash environment you are targeting.
  </Card>
</CardGroup>

<Warning>
  If a customer resides in a jurisdiction where your platform is not permitted to operate, Zero Hash returns a `400` error. Implement a feature flag or pre-check on your side to block customers from restricted states before you call the API. Display a clear error message when a submission is rejected.
</Warning>

<Tip>
  Make participant creation idempotent by passing a `request_id`. If you submit the same `request_id` with different participant data, Zero Hash returns a `400` with the message `"requestID already used with different participant data"`.
</Tip>

## Step 2: Generate a Deposit Address

Once the participant is in `approved` status, generate a deposit address by calling `POST /fund/rfq`. This single call provisions the on-chain address where the customer will send funds.

```json
{
  "participant_code": "CUST01",
  "fund_asset": "USDC.ETH",
  "client_fund_id": "abc123"
}
```

Zero Hash returns a deposit address along with the fee and limit configuration for this participant:

```json
{
  "message": {
    "request_id": "14f8ebb8-7530-4aa4-bef9-9d73d56313f3",
    "participant_code": "CUST01",
    "fund_asset": "USDC.ETH",
    "rate": "1",
    "quoted_currency": "USD",
    "expiry_timestamp": null,
    "deposit_address": "7xKXtg2CW87d97TXJSDpbD5jBkheTqA83TZRuJosgAsU",
    "deposit_fee_bps": 100,
    "subsequent_deposit_fee_floor": "1.00",
    "first_deposit_fee_floor": "1.00",
    "minimum_deposit": "1",
    "maximum_deposit": "500000",
    "reference_id": "abc123"
  }
}
```

Display the `deposit_address` to your customer and instruct them to send the desired amount of the specified asset to that address. The `client_fund_id` you supplied appears as `reference_id` in all subsequent webhook payloads and transaction query responses, making it easy to correlate deposits with your internal records.

<Note>
  The `minimum_deposit` and `maximum_deposit` values are enforced by Zero Hash. Deposits outside these bounds trigger a failure webhook and are not converted to fiat.
</Note>

## Step 3: Deposit Received — What Happens Next

After the blockchain transaction receives the required number of on-chain confirmations (for example, 1 confirmation for USDC on Ethereum), Zero Hash automatically executes the following sequence:

<Steps>
  <Step title="Deposit">
    The inbound crypto is credited to the customer's Zero Hash account.

    | account_owner | account_group | movement_type | asset    | change  |
    |---------------|---------------|---------------|----------|---------|
    | CUST01        | PLAT01        | deposit       | USDC.ETH | +1,000  |
  </Step>
  <Step title="Auto-conversion">
    Zero Hash converts the deposited asset to USD. This creates a trade recorded as `final_settlement` movements.

    | account_owner | account_group | movement_type   | asset    | change  |
    |---------------|---------------|-----------------|----------|---------|
    | CUST01        | PLAT01        | final_settlement| USDC.ETH | -1,000  |
    | CUST01        | PLAT01        | final_settlement| USD      | +1,000  |
  </Step>
  <Step title="Transfer to platform">
    Zero Hash transfers the USD from the customer's account to your platform's master account.

    | account_owner | account_group | movement_type | asset | change  |
    |---------------|---------------|---------------|-------|---------|
    | CUST01        | PLAT01        | transfer      | USD   | -1,000  |
    | PLAT01        | PLAT01        | transfer      | USD   | +1,000  |
  </Step>
</Steps>

## Step 4: Handle the Deposit Webhook

Once the full sequence completes, Zero Hash sends a `DEPOSIT_FUND_COMPLETE` webhook to your configured endpoint.

```json
{
  "participant_code": "CUST01",
  "fund_asset": "USDC.ETH",
  "rate": "1",
  "quoted_currency": "USD",
  "source_address": "3xJ9KzymPqfHBqp2fGKoHtBcEn7LP5gSYNzGKS1vJcBr",
  "deposit_address": "7xKXtg2CW87d97TXJSDpbD5jBkheTqA83TZRuJosgAsU",
  "quantity": "500",
  "notional": "495.00",
  "fund_id": "a1b2c3d4-5678-9012-abcd-ef1234567890",
  "fund_timestamp": 1745262000000000000,
  "deposit_timestamp": 1745261950000000000,
  "transaction_id": "4vJ9GKzymPqfHBqp2fGKoHtBcEn7LP5...",
  "account_label": "general",
  "success": true,
  "reason": "Deposit processed",
  "reference_id": "abc123",
  "raw_fee_bps": "100",
  "deposit_fee_bps": "100",
  "raw_fee_notional": "5.00",
  "deposit_fee_notional": "5.00",
  "source": {}
}
```

Key fields to capture and store:

<ResponseField name="fund_id" type="string">
  The unique identifier for this Account Funding event. Use this to query related movements and cross-reference with your internal records.
</ResponseField>

<ResponseField name="reference_id" type="string">
  Echoes the `client_fund_id` you provided when generating the deposit address. Use this to correlate the event with your own transaction ID.
</ResponseField>

<ResponseField name="success" type="boolean">
  `true` when the full deposit-and-convert flow completed. `false` on any failure; inspect `reason` for the specific error.
</ResponseField>

<ResponseField name="notional" type="string">
  The USD value of the deposit after fees are deducted.
</ResponseField>

<ResponseField name="deposit_fee_notional" type="string">
  The dollar amount of the fee charged on this deposit.
</ResponseField>

## Step 7: Track and Receive Platform Settlement

Zero Hash sends a daily fiat settlement wire to your platform representing the sum of all converted deposits from the prior trading session.

| Session   | Start                   | End                      | Expected Settlement    |
|-----------|-------------------------|--------------------------|------------------------|
| Monday    | Monday 9:00 AM EST      | Tuesday 8:59:59 AM EST   | Tuesday EOD            |
| Tuesday   | Tuesday 9:00 AM EST     | Wednesday 8:59:59 AM EST | Wednesday EOD          |
| Wednesday | Wednesday 9:00 AM EST   | Thursday 8:59:59 AM EST  | Thursday EOD           |
| Thursday  | Thursday 9:00 AM EST    | Friday 8:59:59 AM EST    | Friday EOD             |
| Friday    | Friday 9:00 AM EST      | Monday 8:59:59 AM EST    | Monday EOD             |

<Note>
  During US holidays, expect settlement to arrive by EOD on the next business day.
</Note>

To track the pending settlement amount, query `GET /accounts` with the following parameters to find your platform's USD account:

- `participant_code`: your platform code
- `account_group`: your platform code
- `account_label`: `general`
- `account_type`: `available`
- `asset`: `USD`

To query historical settlements, use `GET /withdrawals/requests?participant_code=PLAT01`. Platform settlements are processed as withdrawals.

## Deposit Returns

<Warning>
  You **cannot** use the deposit's source address as the return destination. Blockchain transactions are not bidirectional, and returning funds to a source address can result in permanent loss. If your platform needs to return a deposit, always collect a verified destination address directly from the customer before initiating the return via `POST /withdrawals/requests`. Contact your Zero Hash sales engineer before implementing a return flow.
</Warning>
