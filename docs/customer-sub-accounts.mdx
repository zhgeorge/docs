Many platforms give customers the flexibility to organize their holdings across multiple accounts — for example, separating a long-term portfolio from an active trading account, isolating positions for tax-lot tracking, or earmarking funds for a specific strategy. Zero Hash supports this pattern through the `account_label` parameter, which lets you tag every deposit, trade, and withdrawal with a platform-defined string identifier. All sub-accounts belong to the same customer identity (a one-to-many relationship between participant and accounts), so a single KYC'd participant can hold as many labeled accounts as your platform requires.

<Info>
  There is no maximum number of sub-accounts. You can create as many `account_label` values as your use case demands without any additional compliance overhead — they all stem from the same verified participant.
</Info>

---

## How Sub-Accounts Work

An account in Zero Hash is uniquely identified by the combination of `participant_code`, `asset`, `account_type`, `account_group`, and `account_label`. Changing the `account_label` on any transaction effectively routes that movement to a separate ledger row, creating an isolated balance view for that label.

## Funding a Sub-Account

To direct an inbound deposit to a specific sub-account, specify the `account_label` when generating the access token for the Account Funding SDK.

### Step 1 — Generate a Funding Access Token with account_label

```json POST /access-tokens — Request
{
  "participant_code": "CUST01",
  "permissions": ["fwc"],
  "deposit_details": {
    "account_label": "account_label_example_1"
  }
}
```

### Step 2 — Customer Deposits Funds

The customer deposits assets (for example, 100 USDC) to the deposit address generated by the SDK. Zero Hash detects the on-chain confirmation, auto-converts to USD, and auto-sweeps to your platform account.

### Step 3 — Zero Hash Ledgers the Deposit

All movements are tagged with the `account_label` you specified. The ledger entries look like this:

| participant_code | account_group | account_label | movement_type | asset | change |
|---|---|---|---|---|---|
| CUST01 | PLAT01 | account_label_example_1 | deposit | USDC | +100 |
| CUST01 | PLAT01 | account_label_example_1 | final_settlement | USDC | −100 |
| CUST01 | PLAT01 | account_label_example_1 | final_settlement | USD | +100 |
| CUST01 | PLAT01 | account_label_example_1 | transfer | USD | −100 |
| PLAT01 | PLAT01 | general | transfer | USD | +100 |

### Step 4 — Receive the Deposit Webhook

Zero Hash sends a webhook to your platform confirming the deposit. The payload includes the `account_label` so you can reconcile in your own system:

```json Deposit Webhook Payload
{
  "participant_code": "CUST01",
  "fund_asset": "USDC",
  "rate": "1",
  "quoted_currency": "USD",
  "source_address": "0x3A45a60c62EE6cD616B1C4510404Eba88116044I",
  "deposit_address": "0xd9aAEc86B65D86f6A7B5B1b0c42FFA531710b6CA",
  "quantity": "500",
  "notional": "500",
  "fund_id": "5155f7c9-95cb-4556-ab89-c178943a7111",
  "fund_timestamp": 1550174574,
  "transaction_id": "a07407e8f98c21b037b4aa0cbc852b8489c5e122fcc3d4b33b7827d0605ad8ff",
  "account_label": "account_label_example_1",
  "success": true,
  "reason": ""
}
```

## Trading into a Sub-Account

You can route settled trade funds into a specific sub-account by including an `account_label` on the relevant party in your `POST /trades` payload.

### Example — Buy BTC into a "Scalping" Account

```json POST /trades — Request
{
  "symbol": "BTC/USD",
  "trade_price": "60000.00000",
  "product_type": "spot",
  "trade_type": "regular",
  "trade_reporter": "reporter@platform.com",
  "platform_code": "DEF456",
  "client_trade_id": "example2",
  "physical_delivery": true,
  "parties_anonymous": false,
  "transaction_timestamp": 1569014063570,
  "parties": [
    {
      "participant_code": "ABC123",
      "asset": "BTC",
      "amount": "2.3",
      "side": "buy",
      "settling": true,
      "account_label": "scalping"
    },
    {
      "participant_code": "DEF456",
      "asset": "USD",
      "amount": "138000.0000",
      "side": "sell",
      "settling": true
    }
  ]
}
```

Funds without an explicit `account_label` settle into the `general` account label by default.

<Tip>
  You can query open positions per sub-account using `GET /positions`. The response includes `account_label` so you can track pending settlements per strategy or goal.
</Tip>

## Withdrawing from a Sub-Account

Each customer has a single global withdrawal address per asset and network. When initiating a withdrawal, specify the `account_label` to debit the correct sub-account balance.

### Step 1 — Link a Withdrawal Account

Use the Account Link SDK (`crypto-account-link` permission) to let the customer register their external withdrawal address. The `account_label` concept is not required at this stage.

### Step 2 — Initiate a Withdrawal with account_label

```json POST /access-tokens — Request (Withdraw SDK)
{
  "participant_code": "CUST01",
  "permissions": ["crypto-withdrawals"],
  "withdrawal_details": {
    "quoted_asset": "USD",
    "withdrawal_request_amount": "100",
    "external_account_id": "cda673db-0334-4151-a80e-8a87015493a4",
    "account_label": "account_label_example_1"
  },
  "reference_id": "5fc7d17d-53d4-480a-a30d-426e29c2ac65"
}
```

### Step 3 — Zero Hash Processes the Withdrawal

Zero Hash auto-converts USD to the target asset (for example, USDC.BASE) and disburses to the linked external address. The ledger reflects:

| participant_code | account_group | account_label | movement_type | asset | change |
|---|---|---|---|---|---|
| CUST01 | PLAT01 | account_label_example_1 | final_settlement | USDC | +100 |
| CUST01 | PLAT01 | account_label_example_1 | withdrawal | USDC | −100 |

### Step 4 — Receive the Withdrawal Webhook

The payment webhook includes `account_label` confirming which sub-account was debited:

```json Withdrawal Webhook Payload
{
  "payment_id": "679ee352-7705-4425-ab4a-16a3d18c1d90",
  "participant_code": "CUST01",
  "asset": "USDC",
  "network": "BASE",
  "payment_type": "payout",
  "quantity": "100",
  "status": "posted",
  "account_label": "account_label_example_1",
  "payment_details": {
    "withdrawal_request_id": "f32a000e-fd71-42b5-ac03-5b23337aa833",
    "destination_address": "0x41D9A0Ee3a917Etmn6182C030dC9f15497eCl22V"
  }
}
```

You can also query historical withdrawals via `GET /payments` or `GET /payments/{payment_id}` — both responses include the `account_label` field.

## Transferring Funds Between Sub-Accounts

If a customer already holds a balance in the `general` account and wants to move it to a custom sub-account, use `POST /transfers`:

```json POST /transfers — Request
{
  "from_participant_code": "ABC123",
  "from_account_group": "DEF456",
  "from_account_label": "general",
  "to_participant_code": "ABC123",
  "to_account_group": "DEF456",
  "to_account_label": "scalping",
  "asset": "BTC",
  "amount": "2.3"
}
```

<Note>
  When transferring between sub-accounts for the same participant, both `from_participant_code` and `to_participant_code` are the same value. Only the `account_label` changes.
</Note>

## Best Practices

- **Namespace your labels** — use a consistent scheme like `user_{id}_strategy_{name}` to avoid collisions across your customer base.
- **Store labels in your database** — Zero Hash does not enforce label uniqueness across participants; your system is the source of truth for which label belongs to which user.
- **Include labels on all related calls** — ensure that trades, deposits, and withdrawals all reference the same `account_label` for a given sub-account to keep ledger entries consistent.
- **Use webhooks for real-time updates** — subscribe to deposit and payment webhooks and use the `account_label` field to update your internal sub-account balance in real time.
